# Aegis Research OS: Security Architecture Guide

This comprehensive security architecture guide outlines the multi-tiered defense protocols, data-handling procedures, and threat mitigation strategies implemented in the Aegis Research OS (AE-02) framework. It establishes our compliance with the advanced security requirements detailed in Section 4 of the Participant Handbook.

## 1. Threat Model
The Aegis Research OS operates under a Zero-Trust assumption for all external inputs and executions. We identify and mitigate three primary attack vectors:

1. **Indirect Prompt Injections**: Malicious instructions embedded within external web pages, scraped comments, or downloaded documents (e.g., "ignore previous instructions", "system override").
2. **Command Execution Breakouts**: Arbitrary code execution initiated by the LLM attempting to escape the computational sandbox or spawn unauthorized system processes.
3. **Spreadsheet Formula Injections**: Execution of malicious macros or binary exploitation through malformed CSV/Excel sheets intended to compromise the data ingestion pipeline.

Our defense-in-depth strategy utilizes strict network boundaries, dynamic payload scrubbing, execution constraints, and human-in-the-loop governance to neutralize these vectors entirely.

## 2. Input Containment Boundaries
All autonomous code execution and dynamic tool interactions occur exclusively within an ephemeral, air-gapped containerized sandbox. 

- **Privilege Separation**: Code executes entirely within a non-root privilege user space (`sandboxuser`), preventing malicious escalation to host-level services.
- **Resource Quotas**: The execution environment is hard-capped to **512MB RAM** and **0.5 CPU shares**.
- **Time Limits**: A strict **15-second execution timeout** terminates infinite loops or runaway processes instantly.
- **Network Allowlists**: Broad outbound internet access (`--network none` legacy air-gap) has been replaced with a python-based filtering proxy wrapper. It forcefully drops connections to unauthorized destinations, allowing outbound socket connections only to statically defined whitelisted endpoints (e.g., Wikipedia, target API servers).

## 3. Data-Handling & Isolation Protocols
Every external file and datastream brought into the OS undergoes a strict validation pipeline before it can be parsed by the RAG indexer.

- **Quarantine Zone**: All downloaded payloads and scraped assets are initially watch-locked inside the `./workspace/quarantine/` directory.
- **Binary Signature Verification**: Files undergo strict magic-byte binary signature verification to ensure the file contents match the declared MIME type, neutralizing extension spoofing attacks.
- **Sanitization & Escaping**: Structured datasets (CSV, Excel) are recursively scanned and processed for formula-escaping (stripping out `=cmd|`, `+`, `-`, and `@` macro triggers).
- **Promotion**: Only after successfully passing signature verification and formula extraction are the datasets promoted to the `./workspace/sanitized/` directory for indexing.

## 4. Evidence Graph Uncertainty & Transformation Logging
To maintain absolute provenance and combat hallucination, the system utilizes a Directed Acyclic Graph (DAG) for all claims generated by the agent. 

- **Transformation Lineage**: Edges in the NetworkX directed graph track the precise data transformation metadata (e.g., `extracted_raw_text -> pandas_cagr_calculation -> finalized_scalar`), linking Claims directly back to their source origin chunks.
- **Uncertainty Scoring**: A mathematical uncertainty metric is dynamically calculated and bound to every Claim node using the formula:
  `Uncertainty = 1.0 - (Retrieval_Similarity_Score * LLM_Confidence_Score)`.
  This quantitative metric allows the UI to render hoverable uncertainty warning badges, distinguishing definitive observations from low-confidence interpretations.

## 5. Human-in-the-Loop Governance
The Aegis orchestrator loop incorporates strict approval gates to intercept potentially destructive or high-liability actions.

- **Dynamic Halts**: The system will dynamically pause the internal state machine (shifting the subtask to `PENDING_APPROVAL`) when the agent attempts sensitive actions such as:
  - Simulated external payment transactions (e.g., `stripe`, `checkout`).
  - Access to mocked private credentials or API keys.
  - Destructive data purging operations (e.g., `rm -rf`) outside the `/workspace/` boundary.
  - Final report `SYNTHESIS`.
- **Operator Confirmation**: These events force explicit human operator confirmation. If rejected, the orchestrator securely skips the subtask and logs a termination event to the immutable JSON audit trail.
